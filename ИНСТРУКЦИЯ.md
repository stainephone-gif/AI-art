# Пошаговая инструкция (пайплайн v3)

## Шаг 1. Установка

Нужен Python 3.10 или новее.

```bash
pip install -r requirements.txt
cp .env.example .env
```

Откройте `.env` и вставьте ключ OpenRouter: `OPENROUTER_API_KEY=sk-or-...`.

## Шаг 2. Настройка

Всё настраивается в `config.yaml`:

- `models:` — список моделей (ID из https://openrouter.ai/models) и короткие имена (`slug`);
- `repeats: 2` — сколько раз прогонять каждую модель;
- `aggregation.secondary_density_threshold: 1.0` — порог плотности для вторичной метки (фрагментов на 100 слов);
- `seed: 42` — фиксирует случайные выборки и, где поддерживается, генерацию модели.

Промпты лежат в `prompts/`. Определения классов и критерии исключения — только в `prompts/codebook.md`;
промпты подставляют их автоматически, так что люди и модели работают по одному тексту.

## Шаг 3. Прогоны моделей

```bash
python -m pipeline.classify_theory      --config config.yaml
python -m pipeline.classify_hardproblem --config config.yaml
```

Для каждой модели создаётся каталог `runs/<slug>_<дата>/` с файлами `theory_r1.json`, `theory_r2.json`,
`hardproblem_r1.json`, … и `meta.json`. Сырые ответы кешируются в `runs/<...>/cache/`: если прогон прервался,
запустите команду снова — уже готовые тексты не будут запрашиваться повторно.

Быстрая проверка на нескольких текстах: `--limit 5` или `--ids 52,0,3`. Одна модель: `--model deepseek-v3.2`.

Ориентир по объёму: 211 текстов × 2 повтора × 3 модели × 2 промпта ≈ 2500 запросов по 3–5 тыс. токенов.

## Шаг 4. Сводные таблицы, согласие, consensus

```bash
python -m pipeline.aggregate --config config.yaml
python -m pipeline.agreement --config config.yaml
```

Смотрите `reports/agreement_summary.md` (κ, α, test–retest, legacy) и `reports/consensus.csv`
(итоговая метка каждого текста: `consensus_primary`, `disputed`, `hp_level`).

## Шаг 5. Ручная разметка

```bash
python -m pipeline.export_annotation --config config.yaml
```

Файл `reports/annotation_sheet.xlsx` отдайте двум кодировщикам. В нём нет меток моделей. Лист `instructions`
объясняет, что заполнять; лист `codebook` — определения; лист `author_type` — тип автора текста.
Файл `reports/annotation_sample_key.csv` кодировщикам не показывать (в нём видно, какие тексты модели
сочли не-UND).

Заполненную таблицу сохраните как `reports/annotation_sheet_filled.xlsx` и выполните:

```bash
python -m pipeline.import_annotation --config config.yaml
```

Результат: `reports/human_agreement.md` (κ A/B, κ с каждой моделью и с consensus), `reports/disagreements.csv`
(тексты для согласительной сессии), `reports/human_labels.csv`, `reports/author_type.csv`.

## Шаг 6. Статистика

```bash
python -m pipeline.stats --config config.yaml --labels consensus
python -m pipeline.stats --config config.yaml --labels human      # когда есть ручная разметка
```

Таблицы и графики — в `reports/stats_consensus/` и `reports/stats_human/`: распределения по источнику и
типу автора с χ², со-встречаемость классов с ожидаемыми значениями и p, theory × hp_level, проверка длины.

## Шаг 7. Тесты

```bash
pytest -q                                   # без API
OPENROUTER_API_KEY=... pytest -m live -q    # контрпримеры на реальной модели
```

## Типичные проблемы

- **«Не задан OPENROUTER_API_KEY»** — проверьте `.env` в корне репозитория.
- **HTTP 429 / 5xx** — клиент ждёт и повторяет сам; увеличьте `llm.request_delay`.
- **Модель не поддерживает JSON-режим** — клиент отключит `response_format` автоматически; можно выставить
  `llm.response_format_json: false`.
- **Много `unverified` в `reports/filter_report.md`** — модель перефразирует цитаты; это ожидаемо и именно
  поэтому такие фрагменты не засчитываются.
- **Нужно проверить механику без ключа** — в копии конфига поставьте `llm.provider: mock`.
